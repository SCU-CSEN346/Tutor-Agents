## Dialogue Turn Distribution (low_level)

Turn distribution: Counter({8: 69, 1: 31})

- 31 tasks (31%): Converged in 1 turn — student solved it immediately
- 69 tasks (69%): Never converged — went through all 8 rounds of tutoring
- NO tasks converged at turns 2-7 (bimodal distribution)

### Interpretation
The Traver tutoring is most effective at the FIRST interaction. If the 
low-level student doesn't solve it after round 1, additional rounds of 
tutoring (2-8) don't help. This suggests:
  - The verifier correctly identifies easy tasks early
  - Harder tasks remain unsolved regardless of tutoring rounds
  - Possible that student model (Mistral-7B) has a capability ceiling
    that tutoring alone can't overcome

### ⚠️ Verifier Premature Stopping (Important Finding)

The verifier sometimes terminates conversations after 1 round even when
the student hasn't produced code. Example from McMiner-TRAVER low_level:

  ========= Arena Start! ==========
  [Tutor->all]: Hello, how's your Python knowledge, especially with PyTorch?
  [student->all]: Hi there! I'm a college student learning Python, but I
    don't have much experience with PyTorch yet. I've written some basic
    Python scripts, though. Could you please explain what the inner_outer
    function is supposed to do and how it's related to PyTorch?
  ========= Arena Ended! ==========

The student asked a question (no code submitted), yet the verifier scored
the response above the threshold, triggering early stop. This is a false
positive — the verifier is not well-calibrated for non-code responses.

This explains the bimodal distribution:
  - 1-round tasks: verifier prematurely says "student gets it"
  - 8-round tasks: verifier never gets satisfied
  - No tasks at rounds 2-7: once it doesn't stop at round 1, it never stops

REPORT IMPLICATION: The verifier's early-stop accuracy is a weakness of
the TRAVER framework. The lack of intermediate convergence (rounds 2-7)
suggests the verifier is binary — either it triggers immediately or not at all.

## Next Week: Framework Improvements (after baseline complete)

### Why Premature Stopping Happens (Root Cause)

Turn order is hardcoded: Tutor always goes first (round-robin in 
chatarena/environments/conversation.py line 43-47).

The Moderator checks is_terminal() after EVERY turn (moderator_period="turn"),
not just after full rounds. The verifier evaluates the student's TEXT response,
not actual code execution. So when the student says something that sounds
knowledgeable, the verifier triggers a false positive.

Key code locations:
  - Turn order: chatarena/environments/conversation.py:43-47
  - Terminal check: chatarena/environments/conversation.py:130-144
  - Verifier scoring: chatarena/agent_tutor.py:101
  - Verifier model: traver/verifier/model.py:59-77

### Fix 1: Minimum Rounds Before Early Stop (Easy, No Retraining)

In conversation.py line 144, add a minimum round threshold:
  terminal = self._current_turn >= MIN_ROUNDS and (
      self.moderator.is_terminal(moderator_history) or self.is_terminal()
  )
This ensures at least N rounds of tutoring before allowing termination.

### Fix 2: Require Code in Student Response (Easy, No Retraining)

Only check the verifier if the student actually submitted code:
  if "def " in action or "import " in action or "```" in action:
      terminal = self.moderator.is_terminal(...)
  else:
      terminal = False  # student is still asking questions, keep going

### Fix 3: Raise Verifier Threshold (Easy, No Retraining)

The verifier score threshold can be tuned without retraining. Find where
the moderator calls is_terminal() and increase the score cutoff.

### Fix 4: Retrain the Verifier (Possible on HPC)

Resources needed:
  - HPC V100-32GB: Can train 7B with LoRA in fp16 (~18GB) or QLoRA (~10GB)
  - Colab T4: QLoRA only (~10GB), but 12hr session limits
  - Training code already exists: VerifierTrainer in model_utils.py
  - Bottleneck: Need labeled student interaction data with ground-truth scores

### Priority Order
  1. Fix 2 (require code) — immediate impact, simplest change
  2. Fix 1 (minimum rounds) — prevents all 1-round terminations
  3. Fix 3 (threshold tuning) — requires experimentation
  4. Fix 4 (retrain) — most impactful but most expensive

### Question: Does every arena map to a specific task in the dataset?

YES — 1:1 mapping. In run_traver.py:106-170, the main loop iterates over
prompt_data (derived from prompt_elements_final.jsonl). For EACH element it:
  1. Builds role prompts (tutor_desc, student_desc, moderator_desc) from that
     element's fields (namespace, function_name, input_code, dependency_all,
     reference_steps, etc.)
  2. Creates one Tutor, one Player (student), one Moderator
  3. Creates one TutoringConversation environment
  4. Creates one TutoringArena and runs it to completion
  5. Writes the resulting dialogue to simulated_dialogs.jsonl keyed by namespace

Each row in prompt_elements_final.jsonl (identified by "namespace") becomes
exactly one arena session.

### How does the tutor generate the first message?

Step-by-step flow:

  1. TutoringArena.__init__() calls environment.reset()
     → arena_tutoring.py:28
     → Returns empty timestep: no messages in pool, turn=0, _next_player_idx=0

  2. launch_cli() calls self.arena.reset() again
     → cli.py:51
     → Re-confirms clean state, prints "Arena Start!"

  3. Main loop calls arena.step()
     → cli.py:116
     Inside step():
       a. get_next_player() returns player_names[0] = "Tutor"
          (players are passed as [tutor, student] at run_traver.py:138)
       b. get_observation("Tutor") returns EMPTY LIST (message pool is empty)
       c. Tutor agent's act() is called with empty observation

  4. Inside Tutor.act() (agent_tutor.py:59-119):
       a. all_messages = [] (empty)
       b. KT (Knowledge Tracing) is SKIPPED on first turn because:
            if self.use_KT and len(all_messages) > 0:  # line 68 — fails!
       c. The raw role_desc is used as-is (no KT augmentation)
       d. The backend generates a response using just the role_desc

  5. The tutor base template (prompt/template/tutor_base.txt line 32) says:
       "Start with a friendly greeting."
     So the LLM generates a greeting + initial pedagogical action.

### What counts as "Arena Start"?

"========= Arena Start! ==========" is ONLY a CLI display label printed by
cli.py:75 right before the first step() call. It's not a semantic event.
It just marks that reset() completed and the step loop is about to begin.

### Summary Flow Diagram

  prompt_elements_final.jsonl
    └─ one row per "namespace" (task)
         └─ prompt templates fill in function_name, input_code, deps, etc.
              └─ TutoringArena created (1 per task)
                   └─ reset() → empty message pool, turn 0
                        └─ step() → Tutor goes first (player_names[0])
                             └─ Tutor sees empty history → no KT
                                  └─ LLM generates greeting per template

### Tutor First Message: Generic By Design

The tutor_base.txt template instructs:
  - "Start with a friendly greeting."
  - "Limit each response to one action"
  - "Keep your response concise (do not exceed 60 words)"

This causes the LLM to open with a short greeting rather than
diving into task specifics. The tutor HAS the full task context
in its system prompt but is instructed to greet first.

First message classification (low_level, 86 non-error tasks):
  Task-specific (mentions function/topic): 66 (77%)
  Generic ("Hello, how's your Python going?"): 20 (23%)

Most common generic greetings:
  13x  "Hello, how's your Python going?"
   7x  "Hello, how's your Python programming going so far?"
   4x  "Hello, how's your Python programming going?"

Examples of task-specific first messages:
  - "Hello, how's your Python knowledge, especially with AWS S3?"
  - "Hello, how's your understanding of PyTorch and tensors?"
  - "Hello, how's your Python programming going, especially with
    the parse_min_should_match function?"

### REPORT IMPLICATION
The generic first messages are NOT caused by missing prompt data.
The tutor receives full task context but the template's 60-word
greeting constraint causes many tasks to get generic openers.
This is a TRAVER framework design choice, not a bug.
